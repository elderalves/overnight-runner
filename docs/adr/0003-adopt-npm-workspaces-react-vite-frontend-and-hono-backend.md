# Adopt npm workspaces, a React + Vite frontend, and Hono for `serve` mode's backend

Deciding [Frontend tech stack & build approach](../../.alves/issues/overnight-runner-web-interface/frontend-stack.md) (see `.alves/` — local, gitignored issue tracker) settles the frontend for the new browser control-plane interface by carrying cezar (`.alves/inspiration/cezar`), this map's visual/IA reference, past look-and-feel into its actual architecture: a real React SPA (routed views, Tailwind, Radix primitives) rather than a hand-rolled buildless one, and a typed API client (`hc<AppType>()`) inferred straight from the server's own route definitions rather than hand-duplicated types. Getting that inference requires the backend to run on Hono, which reverses the bare-`node:http`, no-framework choice [Server architecture & live-update transport for `serve` mode](../../.alves/issues/overnight-runner-web-interface/server-architecture.md) made — that ticket is reopened as a direct consequence, to work out how Hono composes with the in-process `runner.run()` reuse and SSE strategy it already settled.

This sits alongside, not against, [ADR 0002](0002-adopt-typescript-via-node-native-type-stripping.md): 0002's decision — native Node type-stripping, no build step, no runtime dependencies — stays unchanged for the existing CLI/queue-engine code, which becomes its own workspace package (`packages/overnight-runner`) untouched by this ADR. The repo now deliberately carries two build postures side by side: a buildless core package, and a conventionally-built frontend backed by a framework-based server.

## Considered options

- **Hand-rolled buildless frontend + bare `node:http` backend (ADR 0002's posture, extended).** What research and prototyping earlier in this map pointed toward — realistic per [Research: shipping browser-side TypeScript without a bundler](../../.alves/issues/overnight-runner-web-interface/research-buildless-browser-ts.md), and already proven out by the winning visual-design prototype (plain HTML/CSS + one inline `<script>`). Rejected once the destination shifted, in the frontend-stack ticket's grilling session, from "borrow cezar's look" to "reuse cezar's actual component depth and typed-client pattern" — a hand-rolled UI can't reasonably reproduce React Router views, Tailwind, and Radix primitives, or Hono's route-inferred client, without becoming its own framework.
- **React + Vite frontend, hand-written typed client, backend stays bare `node:http`.** A middle option: `packages/contract` (shared request/response types) plus a hand-written `packages/api-client` fetch wrapper against it, with no framework added to the backend. Rejected in favor of adopting Hono outright, in order to get cezar's actual client-inference mechanism (types traced to route handlers, nothing declared twice) rather than a parallel, hand-maintained approximation of it.
- **Full cezar-pattern mirror: npm workspaces (`contract`/`api-client`/`web`/`overnight-runner`), React + Vite for `web`, Hono for the backend (chosen).** Matches cezar's own architecture closely enough that its package boundaries, dependency choices, and dev-workflow split (`vite` dev server and the backend as two separately-run, proxied processes) transfer directly, rather than reinventing an equivalent structure from scratch.

## Consequences

- `packages/overnight-runner` (relocated `lib/`/`bin/`/`test/`) keeps ADR 0002's native-type-stripping, no-build-step, unscoped-package approach — this ADR doesn't touch it, beyond adding `hono` as its first production runtime dependency.
- [Server architecture & live-update transport for `serve` mode](../../.alves/issues/overnight-runner-web-interface/server-architecture.md) is reopened: its bare-`node:http` choice no longer holds, though its SSE-over-HTTP transport and in-process `runner.run()` reuse strategy are expected to carry over onto Hono, not be re-litigated from scratch.
- `packages/web` takes on real dependencies (React, React Router, Tailwind, Radix, `@tanstack/react-query`, etc.) and a real build step (Vite). The root `package.json` becomes a workspace-root manifest only — no code of its own — matching cezar's own root ("publishes nothing itself").
- The dev workflow mirrors cezar's: Vite's dev server and the backend run as two separate, proxied processes, not unified behind a `--dev` flag on `overnight-runner serve`. The shipped `serve` command's production behavior — serving a pre-built `packages/web/dist` — is unaffected by this ADR.
- If a future need arises to drop React/Vite or Hono (the frontend or backend outgrows this shape, or a wider-Node-compatibility need per ADR 0002's own revisit clause resurfaces), that's this ADR's to revisit — not a reopening of ADR 0002, which was never about the frontend or about `serve` mode's backend framework in the first place.
