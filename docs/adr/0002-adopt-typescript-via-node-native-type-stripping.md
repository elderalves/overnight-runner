# Adopt TypeScript via Node's native type-stripping, and switch to ESM

Converting `overnight-runner` from plain JavaScript to TypeScript for compile-time safety on a small, unpublished (`v0.1.0`) codebase. We're running `.ts` source directly through Node's built-in type-stripping rather than compiling to a `dist`/output directory or adding a runtime transpiler. `typescript` and `@types/node` become the project's first-ever dependencies of any kind (`lib/frontmatter.js` currently hand-rolls YAML parsing specifically to avoid a dependency) — accepted as dev-only tooling for `tsc --noEmit` checking, not a change to the zero-runtime-dependency stance.

The module system was originally planned to stay CommonJS, but that was reversed once actually building it: TypeScript never infers real types from a bare `require()` call, in any configuration. The only mechanism that gives typed CommonJS interop is `import x = require(...)` (import-equals) — and that syntax is on Node's unsupported list for native type-stripping (same bucket as `enum`/`namespace`/decorators), because it needs an actual transform, not mere erasure. Concretely, both `require('./frontmatter.ts')` and `require('./frontmatter.ts') as typeof import('./frontmatter.ts')` compiled without error but neither one caught a wrong-argument-type call at the require boundary — confirmed empirically before deciding. Shared interfaces (`Job`, `Frontmatter`, etc.) aren't affected by this — those export/import fine regardless of module system — but function signatures crossing an internal `require()` boundary silently lose all checking, which defeats a large part of the point of converting an 8-file orchestrator to strict TypeScript in the first place. Switching to ESM (`"type": "module"`, real `import`/`export`) was low-cost here specifically: nothing in the codebase uses `__dirname`/`__filename` (the usual ESM migration pain point), and ESM + native stripping is Node's actual first-class-supported combination, with no workarounds needed.

## Considered options

- **Native Node type-stripping (chosen).** No build step, no compiled artifacts, `.ts` files run as-is. Requires bumping `engines.node` from `>=18` to `>=22.18.0` (the first version where stripping is on by default) and giving every internal import/require an explicit `.ts` extension, since Node's TypeScript module resolution — unlike its plain-JS resolution — doesn't fall back to extensionless specifiers. Chosen because nothing here needs pre-22.18 Node, and it's the only option with zero added tooling.
- **Ahead-of-time `tsc` compile** to a separate output directory, `engines.node` unchanged. Rejected: needs a `build`/`prepare` script and a source-vs-output split for a project this size. This option would also have allowed keeping CommonJS with full type safety (via `import = require()`, which only native stripping's erasure-only restriction rules out) — but there was no compensating benefit large enough to reintroduce a build step just to keep CommonJS.
- **Runtime transpiler (`ts-node`/`tsx`).** Rejected: adds a *runtime* dependency, a stronger break from this repo's dependency-avoidance stance than a dev-only type-checker is.
- **Keep CommonJS (original plan, reversed).** Rejected once implementation revealed that CommonJS plus native stripping's erasure-only restriction leaves no mechanism for typed cross-file `require()` calls — only shared interfaces would have been checked, not function signatures. ESM cost nothing extra here (no `__dirname`/`__filename` usage anywhere in the codebase).

## Consequences

- `engines.node` is now `>=22.18.0`; anyone on an older Node can't run the CLI at all.
- The whole codebase is now ESM (`"type": "module"`, `import`/`export`), not CommonJS as originally planned. Every internal import needs an explicit `.ts` extension (e.g. `import './git.ts'`); `bin/overnight-runner` becomes `bin/overnight-runner.ts` so Node's shebang execution type-strips it.
- `typescript` and `@types/node` are the first dependencies (dev-only) this repo has ever had.
- If a future need arises to support older Node (e.g. a wider install base), this should be revisited in favor of ahead-of-time compilation — which would also reopen the CommonJS-vs-ESM question, since a real build step removes the constraint that forced ESM here.
